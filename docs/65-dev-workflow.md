# 개발 워크플로우 (Development Workflow)

## 1. 문서 정보

본 문서는 `saas-crew` 프로젝트의 일관된 코드 품질 유지와 효율적인 배포 프로세스를 정의하기 위한 개발 워크플로우 표준 가이드라인이다. 항공사 승무원 스케줄링 및 정산이라는 도메인 특성상, 데이터 무결성과 정산 로직의 정확성이 최우선이며 이를 위해 엄격한 리뷰 게이트와 릴리스 절차를 적용한다.

### 1.1 문서 이력
| 버전 | 날짜 | 작성자 | 변경 내용 | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| v1.0 | 2024-05-22 | 프로젝트 리드 | 초기 워크플로우 정의 및 sap-16doc 패턴 적용 | 최초 작성 |

### 1.2 적용 범위
- **대상**: `saas-crew` 프로젝트 참여 모든 개발자 및 QA 엔지니어
- **적용 범위**: 로컬 개발, 브랜치 관리, 코드 리뷰, 스테이징 및 프로덕션 배포 전 과정

## 2. 브랜치 전략

본 프로젝트는 Git-flow를 간소화한 **GitHub Flow 기반의 기능 중심 브랜치 전략**을 채택한다. 빠른 반복 개발과 안정적인 릴리스를 동시에 달성하기 위해 `main` 브랜치를 상시 배포 가능한 상태로 유지한다.

### 2.1 브랜치 구조 및 명명 규칙
| 브랜치 유형 | 명명 규칙 | 설명 | 병합 대상 |
| :--- | :--- | :--- | :--- |
| **Main** | `main` | 제품 출시 버전. 항상 안정적인 상태 유지 | - |
| **Develop** | `develop` | 다음 릴리스를 위한 통합 브랜치 | `main` |
| **Feature** | `feat/{issue-number}-{summary}` | 신규 기능 개발 및 UI 구현 (예: `feat/12-schedule-grid`) | `develop` |
| **Fix** | `fix/{issue-number}-{summary}` | 버그 수정 및 로직 오류 해결 (예: `fix/45-calc-error`) | `develop` |
| **Hotfix** | `hotfix/{issue-number}-{summary}` | 운영 환경 긴급 수정 (예: `hotfix/99-auth-fail`) | `main`, `develop` |

### 2.2 브랜치 라이프사이클
1. `develop` 브랜치에서 `feat/` 또는 `fix/` 브랜치를 생성한다.
2. 로컬 개발 완료 후 원격 저장소에 푸시하고 `develop` 브랜치로 PR(Pull Request)을 생성한다.
3. Opus 리뷰 게이트 및 팀원 리뷰 통과 후 `develop`에 병합하며, 해당 기능 브랜치는 즉시 삭제한다.
4. 정기 배포 주기 또는 마일스톤 달성 시 `develop` $\rightarrow$ `main`으로 병합하여 릴리스한다.

## 3. 커밋 메시지 형식

커밋 메시지는 추후 변경 이력 추적과 자동 릴리스 노트 생성을 위해 **Conventional Commits** 표준을 따른다. 모든 메시지는 영문 또는 한글로 작성하되, 일관된 접두사를 사용한다.

### 3.1 커밋 메시지 구조
`type: [scope] subject` (본문 및 꼬리말은 선택 사항)

### 3.2 타입 정의
| 타입 | 설명 | 예시 |
| :--- | :--- | :--- |
| `feat` | 새로운 기능 추가 | `feat: [정산] 토스페이먼츠 API 연동` |
| `fix` | 버그 수정 | `fix: [스케줄] 캘린더 렌더링 겹침 현상 수정` |
| `docs` | 문서 수정 (README, API 명세 등) | `docs: [워크플로우] PR 템플릿 업데이트` |
| `style` | 코드 포맷팅, 세미콜론 누락 등 (로직 변경 없음) | `style: [UI] shadcn/ui 버튼 패딩 조정` |
| `refactor` | 코드 리팩토링 (기능 변경 없음) | `refactor: [DB] Drizzle 쿼리 최적화` |
| `test` | 테스트 코드 추가 및 수정 | `test: [정산] 월별 정산금 계산 유닛 테스트 추가` |
| `chore` | 빌드 업무, 패키지 매니저 설정 등 | `chore: [deps] NextAuth v5 업데이트` |

## 4. PR 템플릿

코드 리뷰의 효율성을 높이고 누락되는 검토 사항을 방지하기 위해 모든 PR은 아래 템플릿을 준수하여 작성한다.

### 4.1 PR 필수 포함 항목
```markdown
## 📌 개요
- 이슈 번호: #
- 작업 내용: (간략하게 작성)

## 🛠️ 변경 사항
- [ ] 변경 사항 1 (예: 정산 로직 내 시간 범위 계산식 수정)
- [ ] 변경 사항 2 (예: 승무원 대시보드 UI 컴포넌트 추가)

## 🧪 테스트 결과
- [ ] 테스트 시나리오: (예: QM 권한으로 스케줄 확정 시 알림 발송 확인)
- [ ] 결과: (성공/실패 및 증빙 스크린샷/로그 첨부)

## ⚠️ 주의 사항 및 리뷰 요청 사항
- 특정 로직의 복잡도가 높아 리뷰어의 집중 검토가 필요한 부분 명시
- 영향 범위: (예: 정산금 계산 $\rightarrow$ PDF 생성 모듈)
```

## 5. Opus 리뷰 게이트

`saas-crew`는 정산 및 자격 관리라는 민감한 데이터를 다루므로, 단순 코드 리뷰를 넘어 **Opus 리뷰 게이트(Opus Review Gate)**라는 엄격한 검증 단계를 거친다.

### 5.1 리뷰 프로세스
1. **1차 자동 검사**: CI 파이프라인을 통해 Lint, Type Check, Unit Test 통과 여부를 확인한다.
2. **2차 동료 리뷰**: 최소 1인 이상의 개발자가 로직의 적절성과 가독성을 검토한다.
3. **3차 Opus 게이트 (최종 승인)**:
    - **검증 대상**: 정산 로직, RBAC 권한 제어, DB 스키마 변경, 외부 API 연동 부분.
    - **검증 기준**: 
        - 정산금 오차 범위 0원 (무결성 보장).
        - RBAC 역할(G, CA, SC, QM, PA, SA)에 따른 접근 제어 누락 여부.
        - PostgreSQL Range Types 활용의 효율성 및 인덱스 전략.
    - **결과**: `Approved` 시에만 `develop` 브랜치 병합 가능.

## 6. 릴리스 절차

릴리스는 `develop` 브랜치에서 검증이 완료된 기능을 `main` 브랜치로 반영하여 실제 운영 환경에 배포하는 과정이다.

### 6.1 단계별 절차
1. **릴리스 후보(RC) 생성**: `develop` 브랜치의 최신 상태를 기반으로 `release/vX.X.X` 브랜치를 생성한다.
2. **스테이징 검증**: Docker self-host 환경의 스테이징 서버에 배포하여 이정훈(매니저), 박소희(승무원) 페르소나 기반의 E2E 테스트를 수행한다.
3. **최종 승인**: North Star Metric(스케줄 확정 소요 시간)에 부정적인 영향이 없음을 확인하고 릴리스를 결정한다.
4. **운영 배포**: `main` 브랜치로 병합 후 Cloudflare Tunnel을 통해 프로덕션 환경에 배포한다.
5. **사후 모니터링**: 배포 직후 30분간 에러 로그 및 DB 커넥션 풀(PgBouncer) 상태를 모니터링한다.

### 6.2 롤백 전략
- 배포 후 치명적인 결함(Critical Bug) 발견 시, `main` 브랜치의 이전 커밋으로 즉시 Revert 하며, `hotfix/` 브랜치를 통해 수정 후 재배포한다.
