# 테스트 계획서 (Test Plan) - saas-crew

## 1. 문서 정보

### 1.1 개요
본 문서는 항공사 객실 승무원 스케줄, 자격 관리 및 정산 SaaS인 `saas-crew` 프로젝트의 품질 보증을 위한 테스트 전략을 정의한다. 본 프로젝트는 복잡한 시간 범위(Range Types) 처리와 정산 데이터의 무결성이 핵심이므로, 단계별 검증 체계를 통해 결함을 최소화한다.

### 1.2 변경 이력
| 버전 | 날짜 | 작성자 | 변경 내용 | 비고 |
| :--- | :--- | :--- | :--- | :--- |

### 1.3 테스트 환경 및 도구

## 2. 단위 테스트 (Unit Test)

### 2.1 전략 및 범위
단위 테스트는 비즈니스 로직의 최소 단위인 함수와 컴포넌트를 대상으로 하며, 외부 의존성을 제거한 상태에서 순수 로직을 검증한다. 특히 정산 계산 로직과 자격 검증 함수는 엣지 케이스를 포함하여 100% 커버리지를 목표로 한다.

### 2.2 주요 테스트 항목
- **정산 로직**: 비행 시간, 직급(CA, SC 등), 수당 체계에 따른 정산 금액 계산 정확도 검증.
- **자격 검증**: 승무원의 자격 만료일과 스케줄 배정 가능 여부를 판단하는 유틸리티 함수 검증.
- **상태 관리**: Zustand 스토어의 상태 변경 및 액션 수행 결과 검증.
- **UI 컴포넌트**: shadcn/ui 기반 공통 컴포넌트의 Props 전달 및 렌더링 상태 검증.

### 2.3 성공 기준
- 핵심 비즈니스 로직(정산, 자격)의 코드 커버리지 90% 이상 달성.
- 모든 단위 테스트 케이스 Pass.

## 3. 통합 테스트 (Integration Test)

### 3.1 전략 및 범위
통합 테스트는 여러 모듈 간의 상호작용과 데이터베이스 연동을 검증한다. `testcontainers`를 사용하여 실제 PostgreSQL 16 환경을 띄워 Drizzle ORM의 쿼리 정확성과 트랜잭션 무결성을 확인한다.

### 3.2 주요 테스트 항목
- **DB 트랜잭션**: 스케줄 확정 시 관련 자격 상태 업데이트 및 로그 기록의 원자성 검증.
- **API 엔드포인트**: Next.js Route Handlers를 통한 요청-응답 사이클 및 HTTP 상태 코드 검증.
- **RBAC 권한 제어**: 역할(G, CA, SC, QM, PA, SA)에 따른 API 접근 제어 및 데이터 필터링 검증.
- **외부 서비스 연동**: 토스페이먼츠 API 모킹을 통한 결제 요청 및 응답 처리 흐름 검증.

### 3.3 성공 기준
- DB 스키마 변경 시 하위 호환성 및 마이그레이션 성공 여부 확인.
- 정의된 RBAC 권한 매트릭스에 따른 접근 제어 성공률 100%.

## 4. UI 테스트 (UI Test)

### 4.1 전략 및 범위
UI 테스트는 사용자가 접하는 화면의 시각적 일관성과 인터랙션의 정확성을 검증한다. Tailwind CSS와 shadcn/ui로 구현된 복잡한 스케줄 캘린더와 데이터 그리드의 렌더링 성능 및 반응형 동작을 확인한다.

### 4.2 주요 테스트 항목
- **스케줄 캘린더**: 드래그 앤 드롭을 통한 스케줄 변경 시 UI 반영 및 상태 업데이트 검증.
- **대시보드 렌더링**: TanStack Query를 통한 서버 데이터 로딩 상태(Loading, Error, Success) UI 처리 검증.
- **반응형 레이아웃**: 모바일(승무원용)과 데스크톱(관리자용) 환경에서의 레이아웃 깨짐 현상 검증.
- **PDF 생성**: Puppeteer를 통해 생성된 정산 명세서의 레이아웃 및 텍스트 정확도 시각적 검증.

### 4.3 성공 기준
- 주요 페이지(스케줄표, 정산서)의 크로스 브라우징(Chrome, Safari, Edge) 호환성 확보.
- UI 인터랙션 시 지연 시간(Latency) 200ms 미만 유지.

## 5. E2E 테스트 (Playwright)

### 5.1 전략 및 범위
Playwright를 사용하여 실제 사용자 페르소나(이정훈, 박소희)의 핵심 워크플로우를 시뮬레이션한다. 프론트엔드부터 백엔드, DB까지 이어지는 전체 흐름을 검증하여 North Star Metric인 '스케줄 확정 소요 시간' 단축을 위한 병목 지점을 확인한다.

### 5.2 주요 시나리오
- **매니저 시나리오 (이정훈)**: 로그인 $\rightarrow$ 월간 스케줄 초안 작성 $\rightarrow$ 승무원 자격 자동 검증 $\rightarrow$ 스케줄 최종 확정 $\rightarrow$ PDF 공지 생성.
- **승무원 시나리오 (박소희)**: 로그인 $\rightarrow$ 확정 스케줄 조회 $\rightarrow$ 정산 명세서 확인 $\rightarrow$ 정산금 지급 요청.
- **결제 시나리오**: 관리자 계정 $\rightarrow$ SaaS 구독 플랜 변경 $\rightarrow$ 토스페이먼츠 결제 완료 $\rightarrow$ 권한 갱신.

### 5.3 성공 기준
- 정의된 핵심 사용자 시나리오(Critical Path)의 Pass Rate 100%.
- E2E 테스트 자동화 파이프라인 구축 및 배포 전 자동 실행.

## 6. 성능 테스트 (k6)

### 6.1 전략 및 범위
k6를 사용하여 시스템의 임계치를 측정하고, 다수의 승무원이 동시에 접속하는 상황에서의 안정성을 검증한다. 특히 PostgreSQL의 Range Types 쿼리와 PgBouncer의 커넥션 풀 효율성을 중점적으로 측정한다.

### 6.2 테스트 지표 및 목표
| 지표 | 목표치 | 근거 |
| :--- | :--- | :--- |
| 평균 응답 시간 (Avg Response Time) | 500ms 이하 | 사용자 경험 유지 임계치 |
| 초당 처리량 (TPS) | 100 TPS 이상 | 동시 접속 승무원 수 및 요청 빈도 추산치 |
| 에러율 (Error Rate) | 0.1% 미만 | 금융/정산 데이터 처리의 안정성 요구사항 |
| 최대 동시 접속자 (Concurrent Users) | 500명 이상 | 타겟 항공사 규모 기반 산정 |

### 6.3 테스트 시나리오
- **부하 테스트 (Load Test)**: 정상 범위 내의 동시 접속자 증가에 따른 응답 시간 변화 측정.
- **스트레스 테스트 (Stress Test)**: 시스템 붕괴 지점까지 부하를 높여 복구 능력(Resilience) 검증.
- **스파이크 테스트 (Spike Test)**: 스케줄 확정 공지 직후 급격한 트래픽 증가 상황 시뮬레이션.

## 7. 보안 테스트 (OWASP ZAP)

### 7.1 전략 및 범위
OWASP ZAP을 활용하여 동적 애플리케이션 보안 테스트(DAST)를 수행한다. NextAuth.js 기반의 인증 체계와 RBAC 권한 부여 로직의 취약점을 탐색하고, 정산 데이터와 같은 민감 정보에 대한 비정상 접근을 차단한다.

### 7.2 주요 점검 항목
- **인증 및 인가**: 세션 하이재킹, 권한 상승(Privilege Escalation) 가능성 점검.
- **입력값 검증**: SQL Injection (Drizzle ORM 사용으로 기본 방어하나 엣지 케이스 확인), XSS 점검.
- **데이터 노출**: API 응답 값에 불필요한 개인정보나 시스템 내부 정보 포함 여부 확인.
- **설정 오류**: Cloudflare Tunnel 및 Docker 환경의 불필요한 포트 개방 및 설정 오류 점검.

### 7.3 성공 기준
- High/Medium 등급의 취약점 0건 달성.
- 발견된 Low 등급 취약점에 대한 조치 계획 수립 및 이행.
