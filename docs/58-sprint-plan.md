# [Sprint Plan] saas-crew: 항공사 객실 승무원 스케줄 및 정산 관리 시스템

## 1. 문서 정보

### 1.1 개요
본 문서는 `saas-crew` 프로젝트의 개발 일정과 단계별 목표를 정의한 스프린트 계획서이다. 본 프로젝트는 항공사 객실 승무원의 복잡한 스케줄링, 자격(Qualification) 검증, 비행 수당 정산을 자동화하는 SaaS 구축을 목적으로 한다.

### 1.2 변경 이력
| 버전 | 날짜 | 작성자 | 변경 내용 | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| v1.0 | 2024-05-22 | Project Manager | 초기 스프린트 계획 수립 및 공수 산정 | 최초 작성 |

### 1.3 핵심 지표 (North Star Metric)
- **지표**: 월간 활성 승무원당 스케줄 확정 소요 시간 (Time-to-Finalize Schedule per Crew)
- **목표**: 수동 배정 방식 대비 스케줄 확정 시간 60% 단축 (기존 엑셀 기반 프로세스 벤치마킹 기준)

## 2. 마일스톤

전체 개발 공정은 총 4개의 주요 마일스톤으로 구분하며, 각 단계는 핵심 기능의 동작 가능 여부(Working Software)를 기준으로 검증한다.

| 마일스톤 | 명칭 | 목표 | 핵심 인도물 | 예상 기간 |
| :--- | :--- | :--- | :--- | :--- |
| M1 | Foundation | 인프라 구축 및 RBAC 권한 체계 수립 | DB 스키마, 인증 모듈, 기본 레이아웃 | 2주 |
| M2 | Core Scheduling | 스케줄 생성 및 자격 검증 로직 구현 | 캘린더 UI, 자격 체크 엔진, 스케줄 API | 4주 |
| M3 | Settlement | 비행 데이터 기반 정산 및 PDF 생성 | 정산 계산기, 토스페이먼츠 연동, PDF 출력 | 3주 |
| M4 | Stabilization | QA, 성능 최적화 및 배포 자동화 | 최종 QA 리포트, Docker 배포 환경 | 2주 |

## 3. Sprint 계획

각 스프린트는 2주 단위로 진행하며, `sap-16doc` 패턴에 따라 기능 단위로 쪼개어 개발한다.

### Sprint 0: 환경 구축 (Foundation)
- **목표**: 개발 환경 셋업 및 데이터 모델 확정
- **주요 과업**:
    - Next.js 14 App Router 및 Drizzle ORM 설정
    - PostgreSQL 16 Range Types를 활용한 스케줄 테이블 설계
    - NextAuth.js v5 기반 RBAC(G, CA, SC, QM, PA, SA) 권한 매핑
    - Cloudflare Tunnel 및 Docker 배포 파이프라인 구축

### Sprint 1: 스케줄 관리 (Scheduling Core)
- **목표**: 매니저(이정훈)가 승무원(박소희)의 스케줄을 배정하고 조회하는 기능 구현
- **주요 과업**:
    - shadcn/ui 기반의 인터랙티브 스케줄 캘린더 구현
    - 승무원별 자격(Qualification) 데이터베이스 구축 및 매칭 로직 개발
    - BullMQ를 이용한 대량 스케줄 업데이트 비동기 처리

### Sprint 2: 정산 및 결제 (Settlement & Payment)
- **목표**: 비행 기록을 바탕으로 한 자동 정산 및 명세서 발행
- **주요 과업**:
    - 비행 시간/구간별 수당 계산 엔진 개발
    - Puppeteer를 활용한 월별 정산 명세서 PDF 자동 생성
    - 토스페이먼츠 API 연동을 통한 구독 결제 및 정산금 지급 프로세스 구현

### Sprint 3: 최적화 및 마무리 (Optimization)
- **목표**: 실사용 환경에서의 성능 검증 및 버그 수정
- **주요 과업**:
    - TanStack Query 캐싱 전략 최적화를 통한 스케줄 조회 속도 개선
    - PgBouncer 설정을 통한 동시 접속 커넥션 풀 최적화
    - 최종 사용자 수용 테스트(UAT) 및 리팩토링

## 4. 공수 산정

공수 산정은 기능 복잡도(Story Point)와 투입 인력을 기준으로 하며, 1 Story Point는 개발자 1인의 1일 집중 작업량을 의미한다.

| 구분 | 기능 단위 | 복잡도(SP) | 예상 공수(MD) | 산출 근거 |
| :--- | :--- | :---: | :---: | :--- |
| **인프라** | DB 설계 및 RBAC 구현 | 5 | 5 | PostgreSQL Range Type 및 권한 매트릭스 설계 |
| **스케줄** | 캘린더 UI 및 배정 로직 | 13 | 13 | 복잡한 드래그 앤 드롭 및 자격 검증 로직 포함 |
| **정산** | 수당 계산 엔진 및 PDF | 8 | 8 | 정산 공식 구현 및 Puppeteer 렌더링 최적화 |
| **결제** | 토스페이먼츠 연동 | 3 | 3 | API 연동 및 웹훅 처리 |
| **공통** | UI/UX 및 상태 관리 | 5 | 5 | Zustand 및 Tailwind CSS 공통 컴포넌트화 |
| **합계** | | **34** | **34** | **총 개발 기간 약 7~11주 (인력 구성에 따라 변동)** |

## 5. 리스크 버퍼

프로젝트 진행 중 발생 가능한 변수를 고려하여 전체 일정의 20%를 리스크 버퍼로 할당한다.

### 5.1 리스크 식별 및 대응 방안
| 리스크 항목 | 영향도 | 발생 가능성 | 대응 방안 |
| :--- | :---: | :---: | :--- |
| **정산 로직 복잡성** | 높음 | 높음 | 항공사별 상이한 수당 체계를 위한 설정 기반(Configuration-based) 엔진 설계 |
| **PDF 생성 성능 저하** | 중간 | 중간 | Puppeteer 프로세스를 BullMQ 큐로 분리하여 백그라운드에서 비동기 처리 |
| **동시 접속 부하** | 중간 | 낮음 | PgBouncer 도입 및 Redis 캐싱 레이어 강화를 통해 DB 부하 분산 |
| **권한 체계 충돌** | 낮음 | 중간 | RBAC 매트릭스를 문서화하고, 미들웨어 단계에서 엄격한 권한 검증 수행 |

### 5.2 버퍼 운용 계획
- **할당 시간**: 총 공수 34MD $\times$ 0.2 $\approx$ **약 7MD**
- **사용 조건**: 
    - 요구사항 변경으로 인한 기능 추가 시
    - 핵심 모듈(정산 엔진 등)의 QA 결함 수정 시
    - 외부 API(토스페이먼츠 등)의 인터페이스 변경 시
